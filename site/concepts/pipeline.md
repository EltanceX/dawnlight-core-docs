# 从配置到一帧画面

<BaselineNote />

一个光影包需要同时回答两类问题：GLSL 怎样计算颜色，以及这些计算什么时候执行、读取什么、写到哪里。JSON 描述后者，并将各个着色器程序连接为可执行的资源与命令关系。

## 五个核心概念

| 概念 | 职责 | 阅读配置时关注什么 |
| --- | --- | --- |
| Phase | 标记宿主提供的执行时机 | 这项工作属于哪个场景阶段？ |
| Pass | 声明一组工作及其 Stage、程序与命令 | 依赖、启用条件和执行位置是什么？ |
| Command | 描述一次实际操作 | 画几何、画全屏、计算、复制还是清理？ |
| Program | 指定着色器入口与编译设置 | 使用哪些 GLSL 文件和编译模式？ |
| Resource | 声明可被读写的数据载体 | 格式、大小、生命周期与生产者是什么？ |

Provider 提供宿主几何提交或其他公共能力，Service 处理相应的宿主服务与状态。它们的 ID 和版本来自当前 Catalog，不能任意编造一个同名字符串就获得新能力。

## 从声明到执行

可以沿着这条路径阅读一个包：

```text
Manifest 与组合文件
    ↓ 加载、引用解析与语义检查
资源 / Program / Pass / Command 的依赖关系
    ↓ 构建候选 generation
按宿主执行时机调用 Stage 和命令
    ↓
读取资源 → 执行着色器或宿主操作 → 写入目标
```

资源与程序声明提供可引用的对象，命令决定它们怎样被使用。同一个 Program 可以被不同的调用配置使用；读取与写入的关系也需要在配置中明确描述。

在 `dawnlight:command_list@1` Stage 中，命令按 Manifest 中的顺序执行。跨 Pass 的依赖、读写危害和阶段方向仍需通过加载与图分析检查，不能把某段文本顺序直接推广为所有阶段的排序规则。

## 七类通用命令

| `type` | 工作 | `program` 规则 |
| --- | --- | --- |
| `fullscreen` | 向命名目标执行全屏绘制 | 必需 |
| `compute` | 计算派发与声明的屏障 | 必需 |
| `copy` | 帧缓冲资源复制 | 不允许 |
| `clear` | 清理命名目标或默认帧缓冲 | 不允许 |
| `present` | 向默认帧缓冲执行最终全屏绘制 | 必需 |
| `engineDraw` | 调用宿主几何 Provider | 可选 |
| `historyCommit` | 标记某个 History 资源本帧完成 | 不允许 |

没有 Program 的命令仍然参与相应的资源或排序分析。例如 `copy` 需要真实的来源读取与目标写入，`historyCommit` 则是生命周期事件，不能用它伪造一次纹理写入。

## JSON、GLSL 与宿主怎样分工

假设你要在场景结果上增加调色：

1. **资源**保存场景颜色，配置决定它的尺寸、格式与生命周期。
2. **Program**引用全屏顶点着色器和调色片元着色器。
3. **Command**将场景颜色绑定到着色器输入，并决定结果写入哪个目标。
4. **GLSL**采样输入并计算新的颜色。
5. **宿主**在对应执行时机调度工作，并管理实际图形资源和状态。

这段说明只建立职责关系。一个合法的外置完整包还必须处理宿主场景接管、整帧目标和回退路径，不能把“有一个后处理着色器”当成“完整场景已经接好”。

## 读一个包时先找什么

先在资源列表中找到场景颜色与深度，再找到生产它们的命令；然后追踪后处理链，直到最终输出。对每条边确认输入 ID、目标、格式和生命周期。

如果找不到资源的生产者，先查看当前启用条件和 BuiltIn fallback，再用 Analyzer 解释当前活动图。接下来阅读[资源、目标与 drawBuffers](./resources-targets)，把“写到哪里”进一步分开理解。
